CM55 Rust Bootstrap 실습 기록

실습 시작일: 2026-11-12 (Asia/Seoul)

대상: Rust 입문자, Cortex-M55 bare-metal 개발 경험자.

진행 방식: 사용자가 실습 명령을 실행하고 소스·설정 파일을 작성한다. 도우미는 단계별 안내와 부연설명을 제공하고 이 HTML 문서를 관리한다. 명령의 실제 결과를 확인한 뒤 완료 상태를 기록한다.

실습 대상 하드웨어

  • 커스텀 Cortex-M55 SoC
  • SRAM 256KB
  • 부트로더 없음, 시작 주소 0x0

SRAM 주소 매핑, 디버거, 프로그램 로딩 방법, FPU·MVE 구성은 실제 보드 실행 단계에서 확인한다.

1단계 — 작업 위치와 도구 확인

상태: 도구 설치 확인 완료 — 사용자 제공 버전 출력 확인.

목표

작업 폴더가 맞는지 확인하고, 터미널에서 Git과 Rust 도구를 실행할 수 있는지 확인한다. 이 단계의 명령은 파일을 생성하거나 패키지를 설치하지 않는다.

직접 실행할 명령

WSL의 Bash 터미널에서 한 줄씩 실행한다. 명령 앞에 별도의 프롬프트 기호를 입력하지 않는다.

cd /root/rust_cm55
pwd
git --version
rustup --version
rustc --version
cargo --version
cc --version

각 명령의 의미

명령목적과 부연설명
cd /root/rust_cm55이후 실습을 진행할 작업 폴더로 이동한다. 정상 실행 시 보통 출력이 없다.
pwd현재 디렉터리의 절대 경로를 출력한다. /root/rust_cm55가 나오는지 확인한다.
git --version소스 변경 이력을 관리하는 Git의 설치 여부와 버전을 확인한다. 저장소 초기화는 별도 단계에서 직접 진행한다.
rustup --versionRust 툴체인 관리 도구다. 컴파일러 버전과 CM55 크로스 컴파일에 필요한 타깃 라이브러리를 설치·관리한다.
rustc --versionRust 컴파일러다. C 개발에서 소스를 컴파일하는 GCC·Clang의 역할에 대응한다.
cargo --versionRust 프로젝트의 빌드, 의존성 관리, 실행, 테스트를 담당한다. C 프로젝트에서 Make/CMake와 패키지 관리 도구가 맡던 역할 일부를 함께 수행한다.
cc --versionPC용 C 컴파일러를 확인한다. PC에서 실행할 첫 Rust 프로그램은 시스템 링커가 필요하며, Ubuntu에서는 보통 C 개발 도구와 함께 제공된다. 이 명령은 CM55용 컴파일러를 확인하는 명령이 아니다.

확인할 결과

pwd의 경로와 각 도구의 버전 출력 또는 오류 메시지를 확인한다. command not found가 나오면 설치가 없거나, 실행 파일을 찾는 경로인 PATH에 등록되지 않았을 수 있다. 오류를 건너뛰어 설치 명령을 실행하지 말고 결과부터 공유한다.

다음 단계

기본 도구 재설치는 건너뛰고 Git 저장소 초기화 단계로 진행한다. 아래 설치 명령은 새 환경을 준비할 때 참고한다.

참고 — 새 Ubuntu/WSL 환경의 설치 명령

참고 절차: 현재는 기본 도구가 모두 있으므로 다시 실행할 필요가 없다. 아래 목록은 이번 단계에서 실행한 명령이나 실행 결과를 뜻하지 않는다.

WSL의 Ubuntu Bash 터미널 기준이다. 아래 시스템 패키지 명령은 현재 환경처럼 root 계정일 때 사용한다. 일반 사용자라면 두 apt-get 명령 앞에 sudo를 붙인다. Rust 설치는 Rust를 사용할 사용자 계정으로 실행한다.

1. 패키지 목록 갱신

apt-get update

Ubuntu 저장소에서 설치 가능한 패키지와 버전의 목록을 내려받는다. 프로그램을 설치하거나 설치된 패키지 전체를 업그레이드하는 명령은 아니다. 이후 설치 명령이 최신 패키지 정보를 사용하도록 먼저 실행한다.

2. Git과 PC 빌드 도구 설치

apt-get install -y --no-install-recommends git build-essential ca-certificates curl
항목역할
git소스와 문서의 변경 이력을 관리한다. 설치와 저장소 초기화는 서로 다른 작업이다.
build-essentialGCC, C/C++ 개발 환경, Make 등의 기본 빌드 도구를 설치한다. 첫 PC용 Rust 실행 파일을 링크할 때 필요한 시스템 링커 환경도 준비한다. CM55용 크로스 컴파일러 설치와는 별개다.
ca-certificatesHTTPS 서버 인증서를 검증할 때 사용하는 신뢰할 수 있는 인증기관 목록을 제공한다.
curlURL의 내용을 내려받는 도구다. 공식 Rust 설치 스크립트 다운로드에 사용한다.
-y패키지 설치 확인 질문에 자동으로 동의한다.
--no-install-recommends필수 의존성을 설치하되 권장 패키지의 자동 설치는 생략한다.

3. 공식 rustup 설치 스크립트 다운로드 및 실행

curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs -o /tmp/rust-cm55-rustup-init.sh
sh /tmp/rust-cm55-rustup-init.sh --profile minimal --default-toolchain stable --component rustfmt --component clippy

첫 명령은 공식 설치 스크립트를 임시 파일로 저장한다. 두 번째 명령은 해당 스크립트를 실행한다. 설치 화면에서 경로와 설정을 확인한 뒤 기본 설치로 진행한다.

--proto '=https'는 HTTPS만 허용하고, --tlsv1.2는 TLS 1.2 이상을 사용한다. -sSf는 진행률 표시를 줄이면서 오류는 표시하고 HTTP 오류를 실패로 처리한다. -o는 저장할 파일 경로를 지정한다.

rustup은 툴체인을 관리하며 함께 설치되는 rustc는 컴파일러, cargo는 프로젝트 빌드 도구다. minimal 프로필에 코드 정렬 도구 rustfmt와 코드 진단 도구 clippy를 추가한다. stable은 설치 시점의 안정 버전을 뜻하므로 설치 날짜에 따라 버전이 달라질 수 있다.

4. 현재 터미널의 PATH 반영

source "$HOME/.cargo/env"

설치된 Rust 도구를 현재 Bash에서 찾도록 환경 설정을 읽는다. PATH는 터미널이 실행 파일을 찾는 디렉터리 목록이다. $HOME은 현재 사용자의 홈 디렉터리이며, root에서는 보통 /root다.

5. 설치 확인

git --version
rustup --version
rustc --version
cargo --version
cc --version
cargo fmt --version
cargo clippy --version

각 명령이 버전을 출력하는지 확인한다. command not found라면 설치 및 PATH를 확인한다. 위 버전 확인만으로 CM55용 코드의 컴파일이나 보드 실행까지 검증되는 것은 아니다.

6. CM55 크로스 컴파일 타깃 설치（해당 실습에서 확인 예정）

rustup target add thumbv8m.main-none-eabi
rustup target list --installed

첫 명령은 해당 bare-metal 타깃의 Rust 라이브러리를 설치하고, 두 번째 명령은 설치된 타깃을 보여준다. thumbv8m.main-none-eabi는 초기 실습에서 사용할 soft-float ABI 타깃 후보다. 실제 CM55 코드 생성에는 CPU 및 FPU·MVE 설정도 따로 확인해야 한다. 이 명령으로 startup 코드, 벡터 테이블, 메모리 맵 또는 디버거가 준비되지는 않는다.

현재 사용자 확인은 기본 도구의 존재에 대한 확인이다. 이 타깃의 설치 여부는 해당 단계에서 별도로 확인한다.

2단계 — Git 저장소 초기화

상태: 완료 — 사용자 제공 초기화 및 상태 출력 확인.

목표

현재 실습 폴더를 Git이 변경 이력을 관리할 수 있는 로컬 저장소로 만든다. Git 설치만으로 특정 폴더의 변경 이력이 자동 관리되지는 않는다.

직접 실행할 명령

cd /root/rust_cm55
git init -b main
git status

각 명령의 의미

git init은 현재 폴더에 Git 관리 정보를 담는 .git을 준비한다. -b main은 최초 브랜치 이름을 main으로 지정한다. 브랜치는 작업 이력의 흐름에 붙인 이름이며, 첫 실습에서는 main 하나로 진행한다.

git status는 현재 브랜치와 파일의 추적 상태를 보여준다. Untracked files는 파일이 존재하지만 아직 Git의 관리 대상으로 등록하지 않았다는 뜻이다. 문서가 있으므로 doc/가 여기에 표시될 수 있다.

예상 결과

On branch main

No commits yet

Untracked files:
  ...
  doc/

위 내용은 예상 예시이며 실제 출력은 경로와 파일 상태에 따라 달라질 수 있다. No commits yet은 아직 저장한 이력 단위인 커밋이 없다는 정상 안내다. 이 단계는 로컬 저장소만 만들며 GitHub 계정이나 원격 저장소가 필요하지 않다.

실행 결과

git init -b main
Initialized empty Git repository in /root/rust_cm55/.git/

git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        doc/
        target/

main 브랜치의 빈 저장소가 정상 생성되었다. 아직 커밋은 없다. doc/와 target/은 모두 미추적 상태다. 문서는 이력에 포함하고 빌드 산출물은 제외하도록 다음 단계에서 설정한다.

3단계 — 빌드 산출물을 Git 관리에서 제외

상태: 완료 — 사용자 git status 출력에서 target/ 제외 확인.

목표와 배경

target/은 Cargo가 사용하는 빌드 산출물 디렉터리다. C 개발의 오브젝트 파일과 실행 파일을 두는 build/와 비슷하다. IDE의 Rust 검사 도구가 실행되면서 생성될 수도 있으며, target/이 존재한다는 사실만으로 실습 빌드가 성공했다고 판단하지 않는다.

재생성할 수 있는 빌드 산출물을 커밋하면 불필요하게 이력이 커진다. .gitignore 파일에 제외 규칙을 작성한다. 파일 자체를 삭제할 필요는 없다.

사용자가 작성할 파일

프로젝트 최상위 /root/rust_cm55에 .gitignore라는 파일을 만들고 다음 한 줄을 입력한 뒤 저장한다. 파일 이름 맨 앞의 점도 포함한다.

/target/

맨 앞의 /는 이 .gitignore가 있는 프로젝트 루트를 기준으로 한다. 맨 뒤의 /는 디렉터리를 뜻한다. 따라서 프로젝트 루트의 target 디렉터리 전체를 무시한다. .gitignore 자체와 doc/는 이후 커밋에 포함할 수 있다.

직접 실행할 확인 명령

git status
git check-ignore -v target/

git status의 미추적 목록에서 target/이 사라지고 .gitignore와 doc/가 보이는지 확인한다. git check-ignore -v는 해당 경로를 무시하게 만든 파일, 규칙의 줄 번호, 규칙을 출력한다.

예상 결과

git check-ignore -v target/
.gitignore:1:/target/ target/

위 예시의 항목 사이 공백은 터미널에서 탭으로 표시될 수 있다. .gitignore는 아직 추적하지 않는 파일에 적용된다. 이번 target/은 앞 단계에서 미추적 상태임을 확인했으므로 이 규칙으로 제외할 수 있다.

실행 결과

git check-ignore -v target/
（출력 없음）

git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        doc/
        target/

target/이 여전히 미추적 목록에 있으므로 제외되지 않았다. 이 경우 git check-ignore -v의 출력이 없는 것은 해당 경로에 적용되는 제외 규칙이 없다는 의미다.

원인 확인과 보완 절차

도우미가 작업 위치와 파일 존재 여부를 읽기 전용으로 확인했다.

pwd
/root/rust_cm55

ls -la .gitignore
ls: cannot access '.gitignore': No such file or directory

프로젝트 루트에 저장된 .gitignore 파일이 없다. 아래 명령을 사용자가 직접 실행해 파일을 만든 뒤 다시 확인한다.

cd /root/rust_cm55
printf '/target/\n' > .gitignore
cat .gitignore
git check-ignore -v target/
git status

printf는 지정한 문자열을 출력하며 \n은 줄바꿈이다. >는 출력을 화면 대신 파일에 기록하는 Bash 리다이렉션이다. 파일이 없으면 생성하고 있으면 내용을 덮어쓴다. 이번에는 파일이 없음을 확인한 상태에서 사용한다. cat은 저장된 내용을 화면에 표시한다.

보완 후 실행 결과

git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        .gitignore
        doc/

target/이 목록에서 사라지고 .gitignore와 doc/만 표시된다. 빌드 산출물 제외 설정을 마쳤다.

4단계 — 첫 커밋에 넣을 파일 준비

상태: baseline 커밋 생성 확인. 이후 Git 가이드는 사용자 요청에 따라 생략한다.

직접 실행할 명령

git add .gitignore doc/
git status
git diff --cached --stat

목적과 부연설명

Git의 기본 흐름은 작업 파일 수정 → git add로 준비 → git commit으로 이력 저장이다. 준비 영역을 스테이징 영역이라고 한다. git add는 실행 시점의 파일 내용을 이 영역에 올린다. 이후 파일을 수정하면 그 수정분은 다시 git add해야 다음 커밋에 포함된다.

이번에는 .gitignore와 doc/만 명시해 추가한다. git status에서 Changes to be committed 아래에 파일이 나타나면 준비된 상태다. git diff --cached --stat은 준비된 변경의 파일별 추가·삭제 줄 수를 요약한다. 아직 커밋을 생성하거나 원격 서버로 전송하지 않는다.

확인할 결과

5단계 — 첫 Rust 프로그램 생성 및 PC 실행

상태: 완료 — 사용자 출력으로 PC용 빌드 및 실행 확인.

목표

먼저 PC에서 실행되는 작은 프로그램으로 Cargo의 생성·빌드·실행 흐름을 익힌다. CM55의 벡터 테이블과 링커 설정은 이후 별도로 다룬다.

사용자가 직접 실행할 명령

cd /root/rust_cm55
cargo init --bin --vcs none .
cargo run

명령과 생성 파일 설명

프로젝트를 별도 lessons 폴더 없이 /root/rust_cm55에 직접 만든다. cargo init은 기존 디렉터리에 Rust 패키지를 초기화한다. 마지막의 점(.)은 현재 디렉터리를 뜻한다. 기존 doc/는 유지한다. --bin은 실행 프로그램을 뜻하고, --vcs none은 버전 관리 초기화를 생략한다. 이미 루트에 Cargo.toml이 있다면 다시 초기화하지 말고 현재 상태를 먼저 확인한다.

생성되는 Cargo.toml은 패키지 이름·버전·Rust edition과 의존성을 기술하는 빌드 설정 파일이다. src/main.rs는 실행 프로그램의 진입 함수 main을 담는다. Cargo.lock은 의존성 버전을 기록하며 Cargo가 관리한다. target/은 프로젝트 루트의 빌드 산출물 디렉터리다. 앞서 작성한 /target/ 제외 규칙이 이 경로에 적용된다.

cargo run은 필요한 빌드를 수행한 뒤 결과 프로그램을 실행한다. 현재 디렉터리의 Cargo.toml을 사용하므로 별도 경로 옵션은 필요하지 않다. 별도 타깃 설정이 없다면 현재 PC용으로 빌드한다.

현재 생성된 파일과 디렉터리

rust_cm55/
├── Cargo.toml
├── Cargo.lock
├── src/
│   └── main.rs
├── target/
├── doc/
│   └── index.html
├── .gitignore
└── .git/

도우미가 현재 파일을 읽어 확인한 구성이다. doc/, .gitignore, .git/은 이전 단계에서 준비한 항목이다. IDE의 Rust 분석 도구도 Cargo를 호출할 수 있으므로 Cargo.lock이나 target/의 존재만으로 사용자의 cargo run 성공을 판단하지 않는다.

Cargo.toml — 프로젝트 설정

[package]
name = "rust_cm55"
version = "0.1.0"
edition = "2024"

[dependencies]

TOML 형식의 텍스트 설정 파일이며 대괄호는 설정 구역을 나눈다. [package]는 패키지 정보다. name은 패키지 이름이고, 기본 실행 파일 이름도 rust_cm55가 된다. version은 이 프로젝트의 버전으로 Rust 컴파일러 버전과는 별개다. edition은 사용할 Rust 언어 규칙의 판이며 2024는 컴파일러 버전 번호가 아니다. [dependencies]에는 사용할 외부 라이브러리를 선언하며 현재는 비어 있다.

C 개발의 Makefile/CMakeLists.txt처럼 빌드 정보를 담지만, Cargo는 src/main.rs 등의 기본 배치를 알고 있어 간단한 프로그램에는 파일 목록이나 컴파일 명령을 따로 작성하지 않는다.

Cargo.lock — 의존성 버전 고정

Cargo가 선택한 라이브러리의 정확한 버전과 의존 관계를 자동 기록한다. Cargo.toml은 원하는 의존성을 선언하고 Cargo.lock은 실제 선택 결과를 담는다. 현재는 외부 의존성이 없어 rust_cm55 패키지 정보만 있다. 보통 직접 수정하지 않는다. 이 파일의 version = 4는 잠금 파일 형식 버전이며 프로젝트나 컴파일러 버전이 아니다.

src/main.rs — 직접 작성할 소스

src는 소스 디렉터리이고 .rs는 Rust 소스 파일 확장자다. main.rs는 현재 실행 프로그램의 소스 시작점이다. C의 main.c에 대응한다고 생각하면 된다. 소스 수정은 사용자가 직접 진행한다.

target/ — 자동 생성되는 빌드 산출물

컴파일 결과, 중간 파일, 검사 캐시 등이 들어간다. 일반적인 cargo run의 PC용 디버그 실행 파일은 target/debug/rust_cm55에 생성된다. IDE가 만든 flycheck 관련 파일도 이 디렉터리에 있을 수 있다. 소스처럼 직접 편집할 대상은 아니다.

기존 파일

doc/index.html은 이 실습의 설명과 결과를 담는 문서이고, .gitignore는 제외 규칙, .git/은 저장소 관리 정보다. 이번 cargo init이 새로 만든 실습 소스와 구분한다.

cargo run은 무엇을 하는가?

cargo run은 현재 프로젝트를 빌드한 뒤 생성한 프로그램을 실행하는 명령이다. 아래는 명령의 동작 설명이며 실제 실행 결과는 이 단계 끝에 기록한다.

  1. Cargo.toml을 읽어 프로젝트 설정과 의존성을 확인한다.
  2. 빌드가 필요하면 rustc를 호출해 소스를 컴파일하고 링크하여 실행 파일을 만든다. 이전 빌드 결과가 최신이면 필요한 작업을 생략한다.
  3. 빌드가 성공하면 생성한 실행 파일을 실행하고 프로그램의 출력을 터미널에 보여준다.

현재 기본 설정에서는 PC용 개발 빌드가 되며 실행 파일 경로는 target/debug/rust_cm55다. C에서 소스를 컴파일·링크한 뒤 ./프로그램으로 실행하는 과정을 한 명령으로 묶은 것과 비슷하다.

cargo build   # 빌드만 수행
cargo run     # 필요한 빌드 후 실행

현재 main 함수가 실행되면 println!이 Hello, world!를 출력하고 프로그램이 종료된다. 현재 명령은 WSL의 Linux 프로그램을 실행한다. CM55에 다운로드하거나 보드를 부팅하는 명령이 아니다.

현재 QEMU가 필요 없는 이유

현재 프로젝트는 기본 설정으로 WSL의 Linux PC에서 실행할 프로그램을 만든다. CM55용 명령어로 빌드하는 단계가 아니므로 이 프로그램을 실행하는 데 QEMU는 필요하지 않다.

이후 CM55용 크로스 컴파일은 실행 파일을 만드는 작업이다. 빌드만 할 때도 QEMU는 필요하지 않다. CM55용 프로그램을 실행하려면 실제 하드웨어 또는 해당 하드웨어 환경을 지원하는 에뮬레이터가 필요하다.

실제 보드에 프로그램을 로드해 실행한다면 QEMU는 필수가 아니다. QEMU를 선택하더라도 CPU뿐 아니라 메모리 맵과 주변장치 등의 보드 모델이 맞아야 한다. 커스텀 SoC를 그대로 실행할 수 있다고 가정하지 않으며, QEMU 사용 여부는 이후 실행 환경을 정할 때 결정한다.

첫 코드 읽기

fn main() {
    println!("Hello, world!");
}

fn은 함수를 선언한다. main은 PC 실행 프로그램의 진입 함수이며, 중괄호 안이 함수 본문이다. println!은 문자열을 출력하고 줄을 바꾸는 매크로다. 느낌표는 일반 함수 호출과 매크로 호출을 구분한다. 세미콜론은 해당 문장을 끝낸다.

이 프로그램은 기본적으로 std 표준 라이브러리와 OS의 출력 기능을 사용한다. CM55 bare-metal에서는 println!의 출력 경로가 자동으로 제공되지 않는다.

Compiling은 패키지를 컴파일하는 단계다. Finished는 빌드 성공을 뜻한다. dev는 개발용 빌드 설정이며 unoptimized + debuginfo는 최적화를 적용하지 않고 디버깅 정보를 포함했다는 뜻이다. Running은 생성한 PC용 실행 파일을 시작했다는 안내이며 Hello, world!는 프로그램 자체의 출력이다. 이번 결과로 PC용 빌드·링크·실행을 확인했다. CM55용 빌드와 보드 실행은 아직 진행하지 않았다.

질문 보충: VCS와 별도 Git 초기화

VCS는 Version Control System, 즉 버전 관리 시스템이며 Git이 여기에 해당한다. --vcs none은 Cargo의 버전 관리 초기화를 생략한다. 기존 Git 저장소를 삭제하거나 비활성화하지 않는다.

Rust 프로젝트 생성과 빌드에 Git은 필수가 아니다. Git 저장소가 없는 일반적인 새 폴더에서는 cargo init --bin .으로 Rust 프로젝트와 Git 저장소를 함께 초기화할 수 있어, 앞선 git init을 별도로 실행하는 것은 필수가 아니었다. 이번에는 기존 Git 저장소에 Rust 프로젝트를 추가했다.

6단계 — 변수와 값 출력

상태: 완료 — 사용자 실행 결과 Count = 1 확인.

사용자가 src/main.rs를 아래 내용으로 수정하고 저장한다.

fn main() {
    let mut count: u32 = 0;
    count += 1;
    println!("count = {count}");
}

mut은 mutable(변경 가능한)의 약자다.

질문 보충 — mut 없는 let과 const의 차이

mut 없는 let은 값을 다시 대입할 수 없는 변수 바인딩이다. 초기값은 프로그램 실행 중에 계산해도 된다. const는 컴파일 시 평가 가능한 상수를 정의한다.

fn double(value: u32) -> u32 {
    value * 2
}

fn main() {
    let count = double(3); // 일반 함수 호출 결과를 담을 수 있음
    const LIMIT: u32 = 10; // 컴파일 시 평가되는 상수, 타입 명시 필수
    println!("count = {count}, limit = {LIMIT}");
}

위 코드는 설명용이며 현재 소스를 수정하라는 지시는 아니다. 일반 fn으로 선언된 double 호출은 const 초기값으로 사용할 수 없다. 컴파일 시 호출 가능한 const fn은 추후 다룬다. let은 타입 추론이 가능하지만 const는 타입을 명시해야 한다. const는 함수 안과 모듈 범위에 선언할 수 있으며, 위 예시의 두 값 모두 다시 대입할 수 없다.

let은 변수를 선언한다. Rust의 변수는 기본적으로 값을 다시 대입할 수 없으며, mut을 붙이면 변경할 수 있다. u32는 C의 uint32_t처럼 부호 없는 32비트 정수다. Rust는 이름 뒤에 콜론과 타입을 적는다. count += 1은 값을 1 증가시키며, 출력 문자열의 {count}는 변수의 값으로 치환된다.

프로젝트 루트에서 직접 실행한다.

cargo run

안내 코드의 예상 프로그램 출력은 count = 1이다. 사용자가 제공한 실제 출력은 다음과 같다.

cargo run
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.00s
     Running `target/debug/rust_cm55`
Count = 1

실제 출력의 첫 글자는 대문자 C다. 값 1이 출력되었으며 실행이 확인되었다. 이번 명령의 출력에는 Compiling이 없으므로 Cargo는 기존 빌드 결과를 재사용했다. 이전 빌드가 어떤 경로로 수행되었는지는 이 출력만으로 확정하지 않는다. 0.00s는 Cargo의 빌드 작업 시간 표시이며 프로그램의 실행 시간을 측정한 값이 아니다.

7단계 — mut 제거 시 컴파일 검사

상태: 의도한 컴파일 실패 확인 / 소스 복구 및 재실행 대기.

목표는 변경 불가능한 변수에 다시 값을 대입하면 실행 전에 오류가 발생함을 확인하는 것이다. src/main.rs에서 let mut count: u32 = 0;의 mut만 제거한다. count += 1;과 나머지 코드는 유지한다.

let count: u32 = 0;
count += 1;

저장한 뒤 프로젝트 루트에서 직접 실행한다.

cargo check

cargo check는 실행 파일을 만들고 실행하는 대신 컴파일 검사를 수행한다. 이번 변경은 의도적으로 오류를 만드는 실습이다. count += 1은 값을 읽는 것뿐 아니라 다시 대입하는 연산이므로, 변경 불가능한 count에 대입할 수 없다는 진단이 예상된다. 실제 오류 메시지를 확인한 뒤 mut을 복구한다.

사용자가 제공한 결과（출력 뒷부분）

  = note: consider using `_count` instead
  = note: `#[warn(unused_variables)]` (part of `#[warn(unused)]`) on by default

warning: value assigned to `count` is never read
 --> src/main.rs:3:5
  |
3 |     count += 1;
  |     ^^^^^^^^^^
  |
  = help: maybe it is overwritten before being read?
  = note: `#[warn(unused_assignments)]` (part of `#[warn(unused)]`) on by default

For more information about this error, try `rustc --explain E0384`.
warning: `rust_cm55` (bin "rust_cm55") generated 2 warnings
error: could not compile `rust_cm55` (bin "rust_cm55") due to 1 previous error; 2 warnings emitted

제공된 출력에는 주 오류 메시지의 앞부분이 없지만 E0384 참조와 실패 요약이 있다.

확인한 소스와 원인

fn main() {
    let count: u32 = 0;
    count += 1;
}

현재 소스에는 mut과 println!이 없다. E0384는 변경 불가능한 변수에 재대입한 오류이며 빌드를 막는다. unused_variables와 unused_assignments는 값을 출력하거나 다른 계산에 사용하지 않아 발생한 경고다. _count는 의도적으로 사용하지 않는 이름을 표시하라는 제안이며 재대입 오류를 해결하는 방법은 아니다.

사용자가 직접 복구할 소스

fn main() {
    let mut count: u32 = 0;
    count += 1;
    println!("Count = {count}");
}

mut으로 재대입을 허용하고 println!으로 최종 값을 읽는다. 저장 후 cargo run을 실행한다. 복구 후 실행 결과는 아직 확인하지 않았다.
