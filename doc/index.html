CM55 Rust Bootstrap 실습 기록

실습 시작일: 2026-11-12 (Asia/Seoul)

대상: Rust 입문자, Cortex-M55 bare-metal 개발 경험자.

진행 방식: 사용자가 실습 명령을 실행하고 소스·설정 파일을 작성한다. 도우미는 단계별 안내와 부연설명을 제공하고 이 HTML 문서를 관리한다. 명령의 실제 결과를 확인한 뒤 완료 상태를 기록한다.

최종 목표와 설계 방향

사용자 지정 목표: 이 저장소에서 커스텀 Cortex-M55 SoC에 Embassy를 구동하고, 간단한 주변장치 드라이버를 구현한다. 이후 양산으로 발전시킬 수 있도록 HAL·드라이버 계층, 소스 트리, 빌드 구성을 체계적으로 설계한다.

현재는 Rust 입문 단계다. 아래는 이후 실습의 설계 기준이며 구현 완료를 의미하지 않는다. 현재 PC용 입문 프로그램을 곧바로 양산 구조로 간주하지 않는다.

  • 부팅·보드 계층: 벡터 테이블, 메모리 맵, 링커 스크립트, 클록과 보드 초기화 책임을 명확히 한다.
  • 레지스터 접근 계층: SoC 레지스터 정의와 저수준 접근을 모으고, unsafe 사용 근거와 범위를 관리한다. SVD 등 제공 자료를 확인한 뒤 생성 방식과 수동 정의 방식을 결정한다.
  • HAL 계층: 주변장치 소유권, 초기화, 인터럽트, DMA, 시간원 및 비동기 동작을 SoC 구현에 맞게 제공한다.
  • 드라이버 계층: 가능한 범위에서 표준 인터페이스를 사용해 SoC 레지스터 접근과 장치의 동작 정책을 분리한다. 단순 HAL 래퍼와 외부 장치 드라이버의 책임을 구분한다.
  • 애플리케이션 계층: Embassy 태스크와 제품 동작을 구성하며 레지스터를 직접 조작하는 코드를 흩뜨리지 않는다.
  • 빌드 구성: PC용 검사·테스트와 CM55 펌웨어 빌드를 구분한다. 적절한 시점에 Cargo workspace를 도입하고 보드·제품 설정 및 의존성 경계를 명시한다.
  • 재현성과 검증: 툴체인·의존성 버전, 빌드 명령과 설정을 관리하고 하드웨어와 독립적인 테스트 및 실제 보드 검증을 구분한다.

실습 순서의 큰 흐름은 Rust 기초 → CM55 부팅과 메모리 초기화 → 기본 주변장치 접근 → 인터럽트·타이머 → Embassy 실행 기반과 시간원 연결 → 간단한 비동기 드라이버 → 제품 확장을 위한 검증과 빌드 정리로 잡는다. 첫 드라이버의 종류와 구체적인 소스 트리는 SoC 자료 및 요구사항을 확인한 뒤 정한다.

설계 시 추가로 확인할 사항은 디버거와 SRAM 로딩 절차, reset 시 주소 매핑, 인터럽트 및 타이머 사양, 주변장치 레지스터 자료, FPU·MVE 구성이다. Embassy 채택만으로 양산 적합성이 확보되는 것은 아니므로 메모리·시간 제약, 오류 복구, 동시성 및 제품별 요구사항을 구현 과정에서 검증한다.

교육 로드맵 — Rust 입문부터 Embassy·드라이버 구현까지

진행 속도 원칙: 사용자가 현재 수준이 적절하며 점진적으로 나아가기를 요청했다. 지금의 난이도를 기준으로 한 번에 새 개념을 하나씩 설명하고, 짧은 코드 작성과 실행 결과 확인, 질문 해소 후 다음 단계로 진행한다. Rust 문법은 기존 C·bare-metal 경험과 연결해 설명하며, 커리큘럼을 빨리 완료하려고 여러 개념이나 소스 구조 변경을 한꺼번에 도입하지 않는다.

교육 과정은 이 저장소에서 순차 진행한다. 아래 과정 번호는 문서에 누적되는 개별 실습 단계 번호와 별개다. 사용자가 직접 소스와 설정을 작성하고, 결과를 확인한 후 다음 과정으로 넘어간다. 각 과정에 명령, 코드 설명, 실제 출력, 문제 해결과 설계 이유를 기록한다.

1단계 — 작업 위치와 도구 확인

상태: 도구 설치 확인 완료 — 사용자 제공 버전 출력 확인.

목표

작업 폴더가 맞는지 확인하고, 터미널에서 Git과 Rust 도구를 실행할 수 있는지 확인한다. 이 단계의 명령은 파일을 생성하거나 패키지를 설치하지 않는다.

직접 실행할 명령

WSL의 Bash 터미널에서 한 줄씩 실행한다. 명령 앞에 별도의 프롬프트 기호를 입력하지 않는다.

cd /root/rust_cm55
pwd
git --version
rustup --version
rustc --version
cargo --version
cc --version

각 명령의 의미

명령목적과 부연설명
cd /root/rust_cm55이후 실습을 진행할 작업 폴더로 이동한다. 정상 실행 시 보통 출력이 없다.
pwd현재 디렉터리의 절대 경로를 출력한다. /root/rust_cm55가 나오는지 확인한다.
git --version소스 변경 이력을 관리하는 Git의 설치 여부와 버전을 확인한다. 저장소 초기화는 별도 단계에서 직접 진행한다.
rustup --versionRust 툴체인 관리 도구다. 컴파일러 버전과 CM55 크로스 컴파일에 필요한 타깃 라이브러리를 설치·관리한다.
rustc --versionRust 컴파일러다. C 개발에서 소스를 컴파일하는 GCC·Clang의 역할에 대응한다.
cargo --versionRust 프로젝트의 빌드, 의존성 관리, 실행, 테스트를 담당한다. C 프로젝트에서 Make/CMake와 패키지 관리 도구가 맡던 역할 일부를 함께 수행한다.
cc --versionPC용 C 컴파일러를 확인한다. PC에서 실행할 첫 Rust 프로그램은 시스템 링커가 필요하며, Ubuntu에서는 보통 C 개발 도구와 함께 제공된다. 이 명령은 CM55용 컴파일러를 확인하는 명령이 아니다.

참고 — 새 Ubuntu/WSL 환경의 설치 명령

참고 절차: 현재는 기본 도구가 모두 있으므로 다시 실행할 필요가 없다. 아래 목록은 이번 단계에서 실행한 명령이나 실행 결과를 뜻하지 않는다.

WSL의 Ubuntu Bash 터미널 기준이다. 아래 시스템 패키지 명령은 현재 환경처럼 root 계정일 때 사용한다. 일반 사용자라면 두 apt-get 명령 앞에 sudo를 붙인다. Rust 설치는 Rust를 사용할 사용자 계정으로 실행한다.

1. 패키지 목록 갱신

apt-get update

Ubuntu 저장소에서 설치 가능한 패키지와 버전의 목록을 내려받는다. 프로그램을 설치하거나 설치된 패키지 전체를 업그레이드하는 명령은 아니다. 이후 설치 명령이 최신 패키지 정보를 사용하도록 먼저 실행한다.

2. Git과 PC 빌드 도구 설치

apt-get install -y --no-install-recommends git build-essential ca-certificates curl
항목역할
git소스와 문서의 변경 이력을 관리한다. 설치와 저장소 초기화는 서로 다른 작업이다.
build-essentialGCC, C/C++ 개발 환경, Make 등의 기본 빌드 도구를 설치한다. 첫 PC용 Rust 실행 파일을 링크할 때 필요한 시스템 링커 환경도 준비한다. CM55용 크로스 컴파일러 설치와는 별개다.
ca-certificatesHTTPS 서버 인증서를 검증할 때 사용하는 신뢰할 수 있는 인증기관 목록을 제공한다.
curlURL의 내용을 내려받는 도구다. 공식 Rust 설치 스크립트 다운로드에 사용한다.
-y패키지 설치 확인 질문에 자동으로 동의한다.
--no-install-recommends필수 의존성을 설치하되 권장 패키지의 자동 설치는 생략한다.

3. 공식 rustup 설치 스크립트 다운로드 및 실행

curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs -o /tmp/rust-cm55-rustup-init.sh
sh /tmp/rust-cm55-rustup-init.sh --profile minimal --default-toolchain stable --component rustfmt --component clippy

첫 명령은 공식 설치 스크립트를 임시 파일로 저장한다. 두 번째 명령은 해당 스크립트를 실행한다. 설치 화면에서 경로와 설정을 확인한 뒤 기본 설치로 진행한다.

--proto '=https'는 HTTPS만 허용하고, --tlsv1.2는 TLS 1.2 이상을 사용한다. -sSf는 진행률 표시를 줄이면서 오류는 표시하고 HTTP 오류를 실패로 처리한다. -o는 저장할 파일 경로를 지정한다.

rustup은 툴체인을 관리하며 함께 설치되는 rustc는 컴파일러, cargo는 프로젝트 빌드 도구다. minimal 프로필에 코드 정렬 도구 rustfmt와 코드 진단 도구 clippy를 추가한다. stable은 설치 시점의 안정 버전을 뜻하므로 설치 날짜에 따라 버전이 달라질 수 있다.

4. 현재 터미널의 PATH 반영

source "$HOME/.cargo/env"

설치된 Rust 도구를 현재 Bash에서 찾도록 환경 설정을 읽는다. PATH는 터미널이 실행 파일을 찾는 디렉터리 목록이다. $HOME은 현재 사용자의 홈 디렉터리이며, root에서는 보통 /root다.

5. 설치 확인

git --version
rustup --version
rustc --version
cargo --version
cc --version
cargo fmt --version
cargo clippy --version

각 명령이 버전을 출력하는지 확인한다. command not found라면 설치 및 PATH를 확인한다. 위 버전 확인만으로 CM55용 코드의 컴파일이나 보드 실행까지 검증되는 것은 아니다.

6. CM55 크로스 컴파일 타깃 설치（해당 실습에서 확인 예정）

rustup target add thumbv8m.main-none-eabi
rustup target list --installed

첫 명령은 해당 bare-metal 타깃의 Rust 라이브러리를 설치하고, 두 번째 명령은 설치된 타깃을 보여준다. thumbv8m.main-none-eabi는 초기 실습에서 사용할 soft-float ABI 타깃 후보다. 실제 CM55 코드 생성에는 CPU 및 FPU·MVE 설정도 따로 확인해야 한다. 이 명령으로 startup 코드, 벡터 테이블, 메모리 맵 또는 디버거가 준비되지는 않는다.

현재 사용자 확인은 기본 도구의 존재에 대한 확인이다. 이 타깃의 설치 여부는 해당 단계에서 별도로 확인한다.

2단계 — Git 저장소 초기화

상태: 완료 — 사용자 제공 초기화 및 상태 출력 확인.

목표

현재 실습 폴더를 Git이 변경 이력을 관리할 수 있는 로컬 저장소로 만든다. Git 설치만으로 특정 폴더의 변경 이력이 자동 관리되지는 않는다.

직접 실행할 명령

cd /root/rust_cm55
git init -b main
git status

각 명령의 의미

git init은 현재 폴더에 Git 관리 정보를 담는 .git을 준비한다. -b main은 최초 브랜치 이름을 main으로 지정한다. 브랜치는 작업 이력의 흐름에 붙인 이름이며, 첫 실습에서는 main 하나로 진행한다.

git status는 현재 브랜치와 파일의 추적 상태를 보여준다. Untracked files는 파일이 존재하지만 아직 Git의 관리 대상으로 등록하지 않았다는 뜻이다. 문서가 있으므로 doc/가 여기에 표시될 수 있다.

예상 결과

On branch main

No commits yet

Untracked files:
  ...
  doc/

위 내용은 예상 예시이며 실제 출력은 경로와 파일 상태에 따라 달라질 수 있다. No commits yet은 아직 저장한 이력 단위인 커밋이 없다는 정상 안내다. 이 단계는 로컬 저장소만 만들며 GitHub 계정이나 원격 저장소가 필요하지 않다.

실행 결과

git init -b main
Initialized empty Git repository in /root/rust_cm55/.git/

git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        doc/
        target/

main 브랜치의 빈 저장소가 정상 생성되었다. 아직 커밋은 없다. doc/와 target/은 모두 미추적 상태다. 문서는 이력에 포함하고 빌드 산출물은 제외하도록 다음 단계에서 설정한다.

3단계 — 빌드 산출물을 Git 관리에서 제외

상태: 완료 — 사용자 git status 출력에서 target/ 제외 확인.

목표와 배경

target/은 Cargo가 사용하는 빌드 산출물 디렉터리다. C 개발의 오브젝트 파일과 실행 파일을 두는 build/와 비슷하다. IDE의 Rust 검사 도구가 실행되면서 생성될 수도 있으며, target/이 존재한다는 사실만으로 실습 빌드가 성공했다고 판단하지 않는다.

재생성할 수 있는 빌드 산출물을 커밋하면 불필요하게 이력이 커진다. .gitignore 파일에 제외 규칙을 작성한다. 파일 자체를 삭제할 필요는 없다.

사용자가 작성할 파일

프로젝트 최상위 /root/rust_cm55에 .gitignore라는 파일을 만들고 다음 한 줄을 입력한 뒤 저장한다. 파일 이름 맨 앞의 점도 포함한다.

/target/

맨 앞의 /는 이 .gitignore가 있는 프로젝트 루트를 기준으로 한다. 맨 뒤의 /는 디렉터리를 뜻한다. 따라서 프로젝트 루트의 target 디렉터리 전체를 무시한다. .gitignore 자체와 doc/는 이후 커밋에 포함할 수 있다.

직접 실행할 확인 명령

git status
git check-ignore -v target/

git status의 미추적 목록에서 target/이 사라지고 .gitignore와 doc/가 보이는지 확인한다. git check-ignore -v는 해당 경로를 무시하게 만든 파일, 규칙의 줄 번호, 규칙을 출력한다.

예상 결과

git check-ignore -v target/
.gitignore:1:/target/ target/

위 예시의 항목 사이 공백은 터미널에서 탭으로 표시될 수 있다. .gitignore는 아직 추적하지 않는 파일에 적용된다. 이번 target/은 앞 단계에서 미추적 상태임을 확인했으므로 이 규칙으로 제외할 수 있다.

실행 결과

git check-ignore -v target/
（출력 없음）

git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        doc/
        target/

target/이 여전히 미추적 목록에 있으므로 제외되지 않았다. 이 경우 git check-ignore -v의 출력이 없는 것은 해당 경로에 적용되는 제외 규칙이 없다는 의미다.

원인 확인과 보완 절차

도우미가 작업 위치와 파일 존재 여부를 읽기 전용으로 확인했다.

pwd
/root/rust_cm55

ls -la .gitignore
ls: cannot access '.gitignore': No such file or directory

프로젝트 루트에 저장된 .gitignore 파일이 없다. 아래 명령을 사용자가 직접 실행해 파일을 만든 뒤 다시 확인한다.

cd /root/rust_cm55
printf '/target/\n' > .gitignore
cat .gitignore
git check-ignore -v target/
git status

printf는 지정한 문자열을 출력하며 \n은 줄바꿈이다. >는 출력을 화면 대신 파일에 기록하는 Bash 리다이렉션이다. 파일이 없으면 생성하고 있으면 내용을 덮어쓴다. 이번에는 파일이 없음을 확인한 상태에서 사용한다. cat은 저장된 내용을 화면에 표시한다.

보완 후 실행 결과

git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        .gitignore
        doc/

target/이 목록에서 사라지고 .gitignore와 doc/만 표시된다. 빌드 산출물 제외 설정을 마쳤다.

4단계 — 첫 커밋에 넣을 파일 준비

상태: baseline 커밋 생성 확인. 이후 Git 가이드는 사용자 요청에 따라 생략한다.

직접 실행할 명령

git add .gitignore doc/
git status
git diff --cached --stat

목적과 부연설명

Git의 기본 흐름은 작업 파일 수정 → git add로 준비 → git commit으로 이력 저장이다. 준비 영역을 스테이징 영역이라고 한다. git add는 실행 시점의 파일 내용을 이 영역에 올린다. 이후 파일을 수정하면 그 수정분은 다시 git add해야 다음 커밋에 포함된다.

이번에는 .gitignore와 doc/만 명시해 추가한다. git status에서 Changes to be committed 아래에 파일이 나타나면 준비된 상태다. git diff --cached --stat은 준비된 변경의 파일별 추가·삭제 줄 수를 요약한다. 아직 커밋을 생성하거나 원격 서버로 전송하지 않는다.

확인할 결과

실행 결과

사용자 실행 결과 대기.

실습 시작점

사용자가 제공한 출력으로 baseline 커밋을 확인했다. 이후 Git 작업은 사용자가 관리한다.

5단계 — 첫 Rust 프로그램 생성 및 PC 실행

상태: 완료 — 사용자 출력으로 PC용 빌드 및 실행 확인.

목표

먼저 PC에서 실행되는 작은 프로그램으로 Cargo의 생성·빌드·실행 흐름을 익힌다. CM55의 벡터 테이블과 링커 설정은 이후 별도로 다룬다.

사용자가 직접 실행할 명령

cd /root/rust_cm55
cargo init --bin --vcs none .
cargo run

명령과 생성 파일 설명

프로젝트를 별도 lessons 폴더 없이 /root/rust_cm55에 직접 만든다. cargo init은 기존 디렉터리에 Rust 패키지를 초기화한다. 마지막의 점(.)은 현재 디렉터리를 뜻한다. 기존 doc/는 유지한다. --bin은 실행 프로그램을 뜻하고, --vcs none은 버전 관리 초기화를 생략한다. 이미 루트에 Cargo.toml이 있다면 다시 초기화하지 말고 현재 상태를 먼저 확인한다.

생성되는 Cargo.toml은 패키지 이름·버전·Rust edition과 의존성을 기술하는 빌드 설정 파일이다. src/main.rs는 실행 프로그램의 진입 함수 main을 담는다. Cargo.lock은 의존성 버전을 기록하며 Cargo가 관리한다. target/은 프로젝트 루트의 빌드 산출물 디렉터리다. 앞서 작성한 /target/ 제외 규칙이 이 경로에 적용된다.

cargo run은 필요한 빌드를 수행한 뒤 결과 프로그램을 실행한다. 현재 디렉터리의 Cargo.toml을 사용하므로 별도 경로 옵션은 필요하지 않다. 별도 타깃 설정이 없다면 현재 PC용으로 빌드한다.

현재 생성된 파일과 디렉터리

rust_cm55/
├── Cargo.toml
├── Cargo.lock
├── src/
│   └── main.rs
├── target/
├── doc/
│   └── index.html
├── .gitignore
└── .git/

도우미가 현재 파일을 읽어 확인한 구성이다. doc/, .gitignore, .git/은 이전 단계에서 준비한 항목이다. IDE의 Rust 분석 도구도 Cargo를 호출할 수 있으므로 Cargo.lock이나 target/의 존재만으로 사용자의 cargo run 성공을 판단하지 않는다.

Cargo.toml — 프로젝트 설정

[package]
name = "rust_cm55"
version = "0.1.0"
edition = "2024"

[dependencies]

TOML 형식의 텍스트 설정 파일이며 대괄호는 설정 구역을 나눈다. [package]는 패키지 정보다. name은 패키지 이름이고, 기본 실행 파일 이름도 rust_cm55가 된다. version은 이 프로젝트의 버전으로 Rust 컴파일러 버전과는 별개다. edition은 사용할 Rust 언어 규칙의 판이며 2024는 컴파일러 버전 번호가 아니다. [dependencies]에는 사용할 외부 라이브러리를 선언하며 현재는 비어 있다.

C 개발의 Makefile/CMakeLists.txt처럼 빌드 정보를 담지만, Cargo는 src/main.rs 등의 기본 배치를 알고 있어 간단한 프로그램에는 파일 목록이나 컴파일 명령을 따로 작성하지 않는다.

Cargo.lock — 의존성 버전 고정

Cargo가 선택한 라이브러리의 정확한 버전과 의존 관계를 자동 기록한다. Cargo.toml은 원하는 의존성을 선언하고 Cargo.lock은 실제 선택 결과를 담는다. 현재는 외부 의존성이 없어 rust_cm55 패키지 정보만 있다. 보통 직접 수정하지 않는다. 이 파일의 version = 4는 잠금 파일 형식 버전이며 프로젝트나 컴파일러 버전이 아니다.

src/main.rs — 직접 작성할 소스

src는 소스 디렉터리이고 .rs는 Rust 소스 파일 확장자다. main.rs는 현재 실행 프로그램의 소스 시작점이다. C의 main.c에 대응한다고 생각하면 된다. 소스 수정은 사용자가 직접 진행한다.

target/ — 자동 생성되는 빌드 산출물

컴파일 결과, 중간 파일, 검사 캐시 등이 들어간다. 일반적인 cargo run의 PC용 디버그 실행 파일은 target/debug/rust_cm55에 생성된다. IDE가 만든 flycheck 관련 파일도 이 디렉터리에 있을 수 있다. 소스처럼 직접 편집할 대상은 아니다.

기존 파일

doc/index.html은 이 실습의 설명과 결과를 담는 문서이고, .gitignore는 제외 규칙, .git/은 저장소 관리 정보다. 이번 cargo init이 새로 만든 실습 소스와 구분한다.

cargo run은 무엇을 하는가?

cargo run은 현재 프로젝트를 빌드한 뒤 생성한 프로그램을 실행하는 명령이다. 아래는 명령의 동작 설명이며 실제 실행 결과는 이 단계 끝에 기록한다.

  1. Cargo.toml을 읽어 프로젝트 설정과 의존성을 확인한다.
  2. 빌드가 필요하면 rustc를 호출해 소스를 컴파일하고 링크하여 실행 파일을 만든다. 이전 빌드 결과가 최신이면 필요한 작업을 생략한다.
  3. 빌드가 성공하면 생성한 실행 파일을 실행하고 프로그램의 출력을 터미널에 보여준다.

현재 기본 설정에서는 PC용 개발 빌드가 되며 실행 파일 경로는 target/debug/rust_cm55다. C에서 소스를 컴파일·링크한 뒤 ./프로그램으로 실행하는 과정을 한 명령으로 묶은 것과 비슷하다.

cargo build   # 빌드만 수행
cargo run     # 필요한 빌드 후 실행

현재 main 함수가 실행되면 println!이 Hello, world!를 출력하고 프로그램이 종료된다. 현재 명령은 WSL의 Linux 프로그램을 실행한다. CM55에 다운로드하거나 보드를 부팅하는 명령이 아니다.

현재 QEMU가 필요 없는 이유

현재 프로젝트는 기본 설정으로 WSL의 Linux PC에서 실행할 프로그램을 만든다. CM55용 명령어로 빌드하는 단계가 아니므로 이 프로그램을 실행하는 데 QEMU는 필요하지 않다.

이후 CM55용 크로스 컴파일은 실행 파일을 만드는 작업이다. 빌드만 할 때도 QEMU는 필요하지 않다. CM55용 프로그램을 실행하려면 실제 하드웨어 또는 해당 하드웨어 환경을 지원하는 에뮬레이터가 필요하다.

실제 보드에 프로그램을 로드해 실행한다면 QEMU는 필수가 아니다. QEMU를 선택하더라도 CPU뿐 아니라 메모리 맵과 주변장치 등의 보드 모델이 맞아야 한다. 커스텀 SoC를 그대로 실행할 수 있다고 가정하지 않으며, QEMU 사용 여부는 이후 실행 환경을 정할 때 결정한다.

질문 보충 — mut 없는 let과 const의 차이

mut 없는 let은 값을 다시 대입할 수 없는 변수 바인딩이다. 초기값은 프로그램 실행 중에 계산해도 된다. const는 컴파일 시 평가 가능한 상수를 정의한다.

fn double(value: u32) -> u32 {
    value * 2
}

fn main() {
    let count = double(3); // 일반 함수 호출 결과를 담을 수 있음
    const LIMIT: u32 = 10; // 컴파일 시 평가되는 상수, 타입 명시 필수
    println!("count = {count}, limit = {LIMIT}");
}

위 코드는 설명용이며 현재 소스를 수정하라는 지시는 아니다. 일반 fn으로 선언된 double 호출은 const 초기값으로 사용할 수 없다. 컴파일 시 호출 가능한 const fn은 추후 다룬다. let은 타입 추론이 가능하지만 const는 타입을 명시해야 한다. const는 함수 안과 모듈 범위에 선언할 수 있으며, 위 예시의 두 값 모두 다시 대입할 수 없다.

let은 변수를 선언한다. Rust의 변수는 기본적으로 값을 다시 대입할 수 없으며, mut을 붙이면 변경할 수 있다. u32는 C의 uint32_t처럼 부호 없는 32비트 정수다. Rust는 이름 뒤에 콜론과 타입을 적는다. count += 1은 값을 1 증가시키며, 출력 문자열의 {count}는 변수의 값으로 치환된다.

질문 보충 — println!은 매크로인가? 어디에 정의되어 있는가?

println!은 Rust 표준 라이브러리 std에서 제공하는 매크로다. 이름 뒤의 느낌표(!)는 일반 함수 호출과 매크로 호출을 구분한다. 표준 라이브러리 소스의 library/std/src/macros.rs에 macro_rules!로 정의되어 있다. 이 경로는 Rust 자체의 소스 트리 기준이며 현재 프로젝트의 파일 경로가 아니다.

println!("Count = {count}");
std::println!("Count = {count}");

위 두 호출은 같은 매크로를 사용한다. 두 번째는 소속 경로 std를 명시한 형태다. 매크로 호출은 컴파일 과정에서 다른 Rust 코드로 확장되며, 실제 출력은 프로그램 실행 시 수행된다. C 매크로와 코드 확장이라는 공통점이 있지만 단순한 텍스트 치환은 아니다.

질문 보충 — use를 따로 선언하지 않아도 되는가?

현재와 같은 일반적인 std 사용 프로그램에서는 println!을 별도의 use 없이 호출할 수 있다. Rust는 자주 쓰는 항목을 프렐루드(prelude)를 통해 자동으로 사용할 수 있게 하며, println!도 std가 자동으로 제공하는 매크로에 포함된다. 모든 표준 라이브러리 항목이 자동으로 이름 범위에 들어오는 것은 아니다.

// println!은 별도 use 없이 사용 가능
fn main() {
    println!("Hello!");
}

// HashMap을 짧은 이름으로 쓰려면 해당 범위에서 가져온다.
// use std::collections::HashMap;

use는 이미 존재하는 항목을 해당 범위에서 짧은 이름으로 참조할 수 있게 하는 선언이다. C의 #include처럼 헤더 파일 내용을 포함하는 동작은 아니다. 위 코드는 설명용이며 현재 실습 소스를 추가로 변경하라는 지시는 아니다.

질문 보충 — use ... as ...로 별칭 붙이기

use 경로 as 별칭; 형태로 항목을 가져올 때 사용할 이름을 지정할 수 있다. 원래 항목의 이름을 바꾸거나 새 함수를 만드는 것이 아니라, use를 선언한 범위에서 같은 항목을 다른 이름으로 참조하게 한다.

use std::println as print_line;

fn main() {
    let count: u32 = 1;
    print_line!("Count = {count}");
}

std의 println 매크로를 print_line이라는 이름으로 가져온 예제다. use에서는 println 뒤에 !를 붙이지 않으며, 매크로를 호출할 때 print_line!처럼 붙인다. 이 코드의 예상 출력은 Count = 1이다. 설명용 예제이며 실행 확인 결과는 아니다.

별칭은 이름 충돌을 피하거나 모듈 이름을 짧게 쓸 때도 사용한다.

use std::fmt::Result as FmtResult;
use std::io::Result as IoResult;

서로 다른 두 Result를 구분하는 예제다. 여기서 as는 가져올 이름의 별칭을 지정한다. 1u32 as u64처럼 값 표현식에서 사용하는 as는 타입 변환으로, 별개의 용법이다.

질문 보충 — C에서는 호출 모양이 같은데 Rust는 왜 !가 필요한가?

println의 이름 자체에는 !가 포함되지 않는다. use std::println;은 이름을 가져오는 선언이며, println!(...)의 !는 매크로 호출 문법이다. 매크로 정의는 macro_rules! 등의 별도 문법을 사용한다.

C의 함수형 매크로는 호출 모양이 함수와 같지만 동작은 다르다. 다음 예제에서 TWICE(1 + 2)는 전처리 시 ((1 + 2) + (1 + 2))로 확장된다. 실제 함수라면 인수 1 + 2를 계산한 값 3을 전달받는다.

#define TWICE(x) ((x) + (x))
int twice(int x) { return x + x; }

TWICE(1 + 2);  // 전처리 시 코드 확장
twice(1 + 2);  // 인수 값을 계산해 함수에 전달

Rust는 호출 위치에서도 이 차이가 드러나도록 함수 호출과 매크로 호출의 문법을 구분한다. !가 없어도 매크로를 지원하는 언어를 설계할 수 있으며 C가 그 예다. !는 코드 확장의 기술적 필수 조건이라기보다 Rust가 선택한 명시적인 문법이다.

twice(1 + 2);          // 함수 호출
println!("{}", 1 + 2); // 매크로 호출
vec![10, 20, 30];      // 매크로는 대괄호 형태로도 호출 가능

함수의 인수 자리에는 표현식이 오지만, 매크로는 자체 규칙에 따라 코드의 토큰을 받아 처리할 수 있다. 예를 들어 vec![0; 4]는 0을 네 개 담는 벡터를 만드는 매크로 호출이다. 이 세미콜론을 사용하는 입력 형태는 일반 함수의 인수 문법과 다르다. vec!는 문법 차이를 보여주는 참고 예시이며 현재 실습에 도입하지 않는다.

이 예제들은 설명용이며 실제 실행 결과를 기록한 것이 아니다. 당장은 이름!(...)를 보면 일반 함수 호출 대신 컴파일 과정의 매크로 확장이 일어난다고 읽으면 된다.

이해 정리 — 사용하는 입장에서 구분이 필요한가?

현재 println!으로 값을 출력하는 단계에서는 !를 호출 문법의 일부로 익히면 충분하다. 다만 매크로는 일반 함수와 인수 처리 규칙이 다를 수 있으므로 모든 매크로를 함수와 동일하게 가정하지 않는다. 사용자는 C의 매크로에서 인수가 중복 평가될 수 있다는 예를 통해 이 차이를 이해했다고 응답했다.

설명 정정: 대화에서 앞서 정의한 TWICE에 count++를 전달하면 두 번 평가된다고 설명했지만, C에서 ((count++) + (count++))는 같은 변수를 순서 보장 없이 변경하므로 정의되지 않은 동작이다. 따라서 결과를 단순히 두 번 증가한다고 예측하면 안 된다. 부작용이 있는 인수를 매크로에 전달할 때 함수와 다른 문제가 생길 수 있다는 취지로 이해한다. 모든 Rust 매크로가 인수를 중복 평가한다는 의미는 아니다.

향후 CM55의 no_std 환경에서는 std::println!을 사용할 수 없다. UART 등 실제 출력 경로와 그에 맞는 출력 구현은 해당 실습에서 마련한다.

8단계 — 정수 타입의 범위

상태: 사용자 요청으로 실행 생략 — 정수 범위 설명과 예상 진단만 참고 기록으로 남김.

u32는 부호 없는 32비트 정수이며 C의 uint32_t에 대응한다. 이번에는 더 작은 u8을 사용해 타입이 담을 수 있는 범위를 확인한다. u8은 부호 없는 8비트 정수로 C의 uint8_t에 대응하며 범위는 0부터 255까지다.

현재 소스에서 선언 한 줄만 다음과 같이 바꾸고 저장한다. 나머지 코드는 유지한다.

let mut count: u8 = 256;

프로젝트 루트에서 cargo check를 직접 실행한다. 256은 u8의 범위를 벗어나므로 기본 설정에서는 컴파일 오류가 예상된다. 이번 실습은 실행 중 덧셈 오버플로가 아니라 초기값 리터럴의 범위 검사다. 사용자 요청으로 이 실습은 실행하지 않고 넘어간다. 위 소스 변경과 명령은 참고 절차이며, 실제 실행 결과나 완료 확인을 뜻하지 않는다. 현재 확인한 소스는 u8과 초기값 0을 사용한다.

9단계 — 함수의 입력과 반환값

상태: 안내 완료 / 사용자 코드 작성 및 cargo run 결과 확인 대기.

현재의 값 증가 연산을 별도 함수로 옮겨 함수 선언, 매개변수와 반환값을 익힌다. 아래 코드는 사용자가 직접 작성할 실습 예제다.

use std::println as print_line;

fn increment(value: u8) -> u8 {
    value + 1
}

fn main() {
    let mut count: u8 = 0;
    count = increment(count);
    print_line!("Count: {count}");
}

fn은 함수를 선언한다. value: u8은 입력 매개변수이며 -> u8은 반환값의 타입이다. 함수 본문의 마지막 표현식 value + 1 뒤에는 세미콜론이 없다. 이 표현식의 값을 함수의 반환값으로 사용하기 때문이다. C의 uint8_t increment(uint8_t value) { return value + 1; }에 대응한다.

이 예제의 u8 값은 함수에 복사되어 전달된다. increment는 호출한 쪽의 count를 직접 변경하지 않으며, 계산 결과를 반환한다. main에서 count = increment(count);로 결과를 다시 대입한다.

저장 후 프로젝트 루트에서 cargo run을 직접 실행한다. 예상 출력은 Count: 1이다. 실제 실행 결과는 아직 확인하지 않았다.

10단계 — if로 값을 선택하기

상태: 사용자 수행 완료 보고 / 현재 소스 확인 완료 — 터미널 출력은 미제공.

사용자의 다음 학습 요청에 따라 if 표현식 설명으로 진행한다. 현재 소스에는 increment 함수가 없어 9단계 작성 및 실행은 확인하지 않았다.

Rust의 if는 조건에 따라 실행할 코드를 나눌 뿐 아니라 값을 만들 수도 있다. C의 count > 0 ? "active" : "idle"과 비교할 수 있다.

use std::println as print_line;

fn main() {
    let mut count: u8 = 0;
    count += 1;

    let status = if count > 0 {
        "active"
    } else {
        "idle"
    };

    print_line!("Count: {count}, status: {status}");
}

조건을 감싸는 괄호는 필요하지 않으며 각 분기의 중괄호는 필요하다. 각 분기의 마지막 문자열 뒤에 세미콜론을 붙이지 않아 그 값을 분기의 결과로 사용한다. 마지막 };의 세미콜론은 let 선언을 끝낸다. 값을 선택해 대입하는 이 형태에서는 else가 필요하고 양쪽 분기의 결과 타입이 맞아야 한다.

사용자가 저장 후 cargo run을 실행한다. 예상 출력은 Count: 1, status: active다. 비교를 위해 count += 1;을 주석 처리하면 예상 출력은 Count: 0, status: idle이다. 이 경우 mut이 불필요하다는 경고가 나올 수 있다. idle 분기 실행 결과는 아직 확인하지 않았다.

사용자 작성 코드와 자동완성 차이

사용자가 수행했다고 보고했으며 자동완성으로 예제와 약간 다를 수 있다고 설명했다. 도우미가 현재 소스를 읽어 다음 내용을 확인했다.

use std::println as print_line;
fn main() {
    let mut count: u8 = 0;
    count += 1;

    let status = if count > 0 { "active" } else { "idle" };
    print_line!("Count: {}, Status: {}", count, status);
}

if를 한 줄에 작성해도 의미는 같다. 출력문의 {}는 뒤에 나열한 count와 status를 순서대로 사용한다. 앞서 안내한 {count}, {status}는 변수 이름을 문자열 안에 직접 쓰는 형태이며 두 방식 모두 유효하다. 사용자 코드의 Status는 대문자 S이므로 예상 출력은 Count: 1, Status: active다. 이는 소스를 바탕으로 예상한 출력이며 사용자의 터미널 출력을 직접 확인한 기록은 아니다.

질문 보충 — if 블록 안에서 작업하기

앞선 let status = if ... 형태는 C의 조건 연산자처럼 값을 선택하는 예제였다. Rust에서도 C처럼 if 블록 안에서 출력, 함수 호출, 변수 변경 등의 작업을 수행할 수 있다.

if count > 0 {
    print_line!("active");
    print_line!("Count: {count}");
} else {
    print_line!("idle");
}

조건이 참이면 첫 블록을, 거짓이면 else 블록을 실행한다. 블록 안에는 여러 문장을 작성할 수 있으며, 위 호출 뒤의 세미콜론은 각 문장을 끝낸다. 이 형태의 if 전체 뒤에는 세미콜론이 필요하지 않다. 거짓일 때 수행할 작업이 없으면 else를 생략할 수도 있다.

바깥 변수에 대입하는 형태도 가능하다. 이때 변수는 mut으로 선언되어 있어야 한다.

let mut status = "idle";
if count > 0 {
    status = "active";
}
print_line!("Status: {status}");

차이는 if가 만든 값을 let으로 받는지, 블록 안에서 필요한 작업을 수행하는지에 있다. Rust의 if는 표현식이며, 위와 같이 결과 값을 사용하지 않는 형태로도 쓸 수 있다. 조건에는 bool이 필요하므로 C의 if (count) 대신 if count != 0처럼 작성한다.

위 코드는 설명용이다. 사용자 소스는 변경하지 않았고 해당 예제의 실행 결과도 확인하지 않았다.

질문 보충 — 나머지 연산과 if 코드 확인

정수의 %는 나머지 연산자다. count = count % 10;은 count %= 10;으로 줄일 수 있다. 23 % 10은 3, 10 % 10은 0이다. count를 변경하므로 mut 선언이 필요하며, 앞에 //를 붙이면 주석이 되어 실행되지 않는다.

현재 소스 확인

use std::println as print_line;
fn main() {
    let mut count: u8 = 0;
    count += 1;
    if count > 10 {
        print_line!("Count exceeded 10!");
        count = 0;
    }

    let status = if count > 0 { "active" } else { "idle" };
    print_line!("Count: {}, Status: {}", count, status);
}

현재 코드는 조건이 참이면 출력과 재대입을 수행하는 if 블록과, 조건에 따라 값을 선택하는 if 표현식을 모두 사용한다. % 연산은 현재 소스에 없다.

0에서 한 번만 증가하므로 count는 1이고 count > 10은 거짓이다. 예상 출력은 Count: 1, Status: active다. 실행할 때마다 count를 0으로 초기화하므로 실행 횟수는 누적되지 않는다.

count > 10은 11 이상에서 참이다. 10에 도달했을 때 초기화하려면 count >= 10으로 작성한다. 0으로 초기화하는 동작과 % 10으로 나머지를 구하는 동작은 다르다. 예를 들어 11 % 10은 1이다.

소스 검토 기록이며 이번 검토에서 프로그램을 대신 실행하거나 사용자 소스를 수정하지 않았다.

11단계 — while 반복과 복수 조건 검사

상태: 사용자 작성 소스 및 제공한 출력 뒷부분 확인 완료.

사용자가 증가 연산 위에 while 반복을 추가하자고 제안했다. 도우미는 while count <= 10 예제와, 반복 안에서 count를 0으로 초기화하면 반복이 끝나지 않음을 설명했다. 이후 사용자가 작성한 실제 소스는 다음과 같다.

use std::println as print_line;
fn main() {
    let mut count: u8 = 0;

    while count < 15 {
        count += 1;
        if count % 3 == 0 {
            print_line!("Count is a multiple of 3: {}", count);
        }
        if count > 10 {
            print_line!("Count exceeded 10!");
        }

        let status = if count > 0 { "active" } else { "idle" };
        print_line!("Count: {}, Status: {}", count, status);
    }
}

사용자가 제공한 실행 결과（뒷부분）

Count: 10, Status: active
Count exceeded 10!
Count: 11, Status: active
Count is a multiple of 3: 12
Count exceeded 10!
Count: 12, Status: active
Count exceeded 10!
Count: 13, Status: active
Count exceeded 10!
Count: 14, Status: active
Count is a multiple of 3: 15
Count exceeded 10!
Count: 15, Status: active

처음에는 사용자가 Count: 16, Status: active를 공유했으나 이후 위와 같이 15로 끝나는 출력을 제공했다. 현재 소스와 일치하는 것은 위 출력이다.

while은 본문에 들어가기 전에 조건을 검사한다. count가 14일 때 조건을 만족하여 본문에 들어가고, 15로 증가한 뒤 출력한다. 다음 검사에서 15 < 15가 거짓이므로 종료한다. 이 소스에서는 Count: 16이 출력되지 않는다.

count % 3 == 0은 3의 배수를 검사한다. 두 if는 독립적이므로, 12와 15에서는 3의 배수라는 메시지와 10을 넘었다는 메시지가 모두 출력된다. 조건을 만족할 때마다 실행하므로 10 초과 메시지는 11부터 15까지 매번 출력된다. status를 계산하는 시점에는 count가 항상 양수이므로 모두 active가 된다.

12단계 — for와 정수 범위

상태: 사용자 작성 소스 확인 완료 / 실행 결과는 미제공.

Rust의 for는 범위 등의 항목을 순서대로 꺼내며 반복한다. C의 for (int count = 1; count <= 15; count++)에 해당하는 반복을 다음처럼 작성할 수 있다.

use std::println as print_line;

fn main() {
    for count in 1u8..=15 {
        if count % 3 == 0 {
            print_line!("Count is a multiple of 3: {}", count);
        }
        if count > 10 {
            print_line!("Count exceeded 10!");
        }

        let status = if count > 0 { "active" } else { "idle" };
        print_line!("Count: {}, Status: {}", count, status);
    }
}

1u8은 u8 타입의 값 1이다. 여기서는 이전 실습의 count 타입을 유지하도록 명시했다. 1u8..=15는 1부터 15까지 끝값을 포함한다. 1u8..15는 1부터 14까지로 끝값을 제외한다.

기존의 let mut count: u8 = 0;과 count += 1;은 제거한다. for가 각 반복의 count를 새로 바인딩하므로 직접 증가시키거나 mut을 붙일 필요가 없다. count는 for 본문에서 사용할 수 있으며 반복문 뒤에서는 이 바인딩을 사용할 수 없다.

사용자가 직접 수정하고 cargo run으로 확인한다. 예상 동작은 앞선 while 실습과 같으며, Count는 1부터 15까지 출력된다. 3의 배수 메시지와 10 초과 메시지도 동일한 값에서 출력된다. 위는 안내 예제의 예상 동작이며 실제 실행 결과는 아직 확인하지 않았다.

시작값 질문과 실제 작성 코드 확인

사용자가 1u8이 초기값 1을 뜻하는지 질문했다. 첫 반복의 count가 1이라는 의미이며, 정확히는 범위가 제공하는 값을 매 반복마다 count에 바인딩한다. 0u8..=15로 작성하면 0부터 15까지 총 16번 반복한다.

이후 소스를 확인한 결과 실제 반복 범위는 아래와 같다.

for count in 1u8..15 {
    // 기존 조건 검사와 출력
}

이는 올바른 for 문법이며, 끝값을 제외하므로 1부터 14까지 총 14번 반복한다. 안내한 1u8..=15와 달리 15는 출력하지 않는다. 15까지 포함하려면 ..=15로 작성한다. 실제 소스의 마지막 예상 출력은 Count: 14, Status: active다. 3의 배수 메시지는 3, 6, 9, 12에서, 10 초과 메시지는 11부터 14까지 출력될 것으로 예상된다. 소스만 검토했으며 사용자 코드 수정이나 실행은 하지 않았다.

반복 제어 — break와 continue

C와 마찬가지로 break는 가장 가까운 반복문을 종료하고, continue는 현재 회차의 나머지 코드를 건너뛰고 다음 반복으로 진행한다. for와 while에서 모두 사용할 수 있다.

use std::println as print_line;

fn main() {
    for count in 1u8..=10 {
        if count == 3 {
            continue;
        }
        if count == 6 {
            break;
        }

        print_line!("Count: {count}");
    }
    print_line!("Done");
}

3에서는 출력문을 건너뛰고 다음 값인 4로 진행한다. 6에서는 반복문을 종료하므로 6부터 10까지 출력하지 않는다. 반복문이 끝난 뒤의 Done은 실행된다.

Count: 1
Count: 2
Count: 4
Count: 5
Done

while에서 continue를 쓰면 조건 검사로 돌아간다. 직접 작성한 증가 코드가 continue 뒤에 있으면 건너뛰어 반복이 끝나지 않을 수 있으므로 위치에 유의한다.

상태: 보충 설명 및 예상 출력 기록 — 사용자 소스는 수정하지 않았으며 실제 실행 결과는 아직 확인하지 않음.

질문 보충 — for의 증가 간격 지정

C의 for처럼 증가식을 직접 적지는 않지만, 범위에 step_by를 적용해 반복 간격을 지정할 수 있다.

// C: for (uint8_t count = 1; count <= 15; count += 2)
for count in (1u8..=15).step_by(2) {
    print_line!("Count: {count}");
}

예상 count 값은 1, 3, 5, 7, 9, 11, 13, 15다. 괄호는 범위 전체에 step_by를 적용하도록 묶는다. step_by(2)는 범위에서 값을 두 칸 간격으로 꺼낸다. step_by(0)은 사용할 수 없으며 호출하면 panic이 발생한다.

현재 소스의 1u8..15는 끝값을 제외하므로, for count in (1u8..15).step_by(2)로 바꾸면 1, 3, 5, 7, 9, 11, 13을 사용한다. 가변적인 증가 규칙이 필요하면 while에서 직접 값을 갱신하는 방법을 사용할 수 있다.

설명용 예제이며 사용자 소스는 수정하지 않았다. 실제 실행 결과도 아직 확인하지 않았다.

질문 보충 — for에 별도 조건식 넣기

Rust에는 C의 for (초기화; 조건; 갱신) 형태가 없다. C에서 다음처럼 작성하는 반복은 Rust에서 while로 표현할 수 있다.

// C: for (int count = 1; count < 15 && ready; count += 2)
let mut count = 1;

while count < 15 && ready {
    // 작업
    count += 2;
}

또는 for 본문에서 조건을 검사하고 break로 반복을 종료할 수 있다.

for count in (1u8..15).step_by(2) {
    if !ready {
        break;
    }

    print_line!("Count: {count}");
}

위 예제의 ready는 앞에서 선언된 bool 변수라고 가정한다. &&는 논리 AND이고 !ready는 논리 부정이며, break는 가장 가까운 반복문을 빠져나간다.

상태: 사용자 요청으로 설명만 기록 — 소스 수정 및 실행 실습은 진행하지 않음.

질문 보충 — Rust에서는 while을 더 많이 쓰는가?

C의 for에서 복잡한 조건식과 갱신식을 사용했다면 Rust에서는 while로 옮기는 경우가 있다. 다만 이것만으로 Rust에서 while의 사용 빈도가 더 높다고 판단할 수는 없다. Rust의 for는 범위나 배열의 값을 직접 순회할 수 있다.

// 정해진 횟수만큼 반복
for count in 0..10 {
    // 작업
}

// 배열의 값을 순서대로 처리 (values는 앞서 정의한 배열)
for value in values {
    // 작업
}

// 상태 조건이 유지되는 동안 반복 (ready는 bool)
while ready {
    // 작업
}

값들을 순서대로 처리할 때는 for, 상태 조건에 따라 반복할 때는 while을 선택하는 기준으로 이해한다. 위 코드는 개념 설명용이며 실행 결과를 확인한 실습은 아니다.

13단계 — 배열과 for 순회

상태: 안내 완료 / 사용자 코드 작성 및 실행 결과 확인 대기.

배열은 같은 타입의 값을 정해진 개수만큼 묶는다. C의 uint8_t values[4] = {3, 6, 9, 12};에 대응하는 Rust 선언은 다음과 같다.

let values: [u8; 4] = [3, 6, 9, 12];

[u8; 4]는 u8 원소가 네 개 있는 배열 타입이다. 대괄호 안의 세미콜론은 원소 타입과 개수를 구분한다. 오른쪽 대괄호 안에는 실제 원소 값을 나열한다. 이 배열 자체는 동적 메모리 할당을 요구하지 않는다.

use std::println as print_line;

fn main() {
    let values: [u8; 4] = [3, 6, 9, 12];

    for value in values {
        print_line!("Value: {value}");
    }
}

이전에는 for가 정수 범위에서 값을 꺼냈고, 이번에는 배열의 원소를 순서대로 꺼낸다. 인덱스 변수나 직접 작성한 증가식 없이 원소 네 개를 처리한다.

사용자가 직접 작성하고 cargo run을 실행한다. 다음은 예상 출력이며 실제 결과는 아직 확인하지 않았다.

Value: 3
Value: 6
Value: 9
Value: 12

질문 보충 — 배열 초기값을 생략하면 어떻게 되는가?

Rust에서 초기화하지 않은 지역 배열을 읽을 수 없다. 초기값을 생략했다고 자동으로 0이 채워지지 않으며, 초기화되지 않은 값을 읽으려 하면 컴파일 오류가 발생한다.

let values: [u8; 4];
print_line!("{}", values[0]); // 오류: 초기화 전에 사용

모든 원소를 0으로 초기화하려면 명시적으로 작성한다.

let values: [u8; 4] = [0; 4];
// [0, 0, 0, 0]

타입의 [u8; 4]는 원소 타입과 개수를 나타내고, 초기값의 [0; 4]는 값 0을 네 번 반복해 채운다는 뜻이다.

let values = [7u8; 4];
// [7, 7, 7, 7]

[]는 원소가 없는 길이 0의 배열이다. 길이 4인 배열의 초기값을 생략한다는 의미가 아니다. 필요하면 let empty: [u8; 0] = [];처럼 원소 타입을 명시할 수 있다.

상태: 사용자 요청으로 설명 기록 — 위 예제의 실행 결과는 확인하지 않았으며 소스는 수정하지 않음.
